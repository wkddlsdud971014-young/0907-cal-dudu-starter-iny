v1 → v2 무엇이 다른가

새 기능을 얹지 않는다. 이미 DB에 있는 사실을 고객 쪽으로 한 겹 더 연다.

v1은 기다림에 기한을 붙였다(회신 기한·경과 시간·진행 타임라인). v2는 마감을 미리 읽게 한다. 접수는 점유가 아니므로 한 슬롯에 여러 명이 겹칠 수 있는데, 지금 고객은 그 사실을 마감된 뒤에야 안다. 겹친 수를 신청 시점에 보여주면 ③의 “당황”이 “예상했음”으로 바뀐다. 고정 규칙은 한 줄도 건드리지 않는다.

작업 순서

확실한 것을 먼저 끝내고, 정책 SQL을 건드리는 것을 마지막에 둔다. 앞의 셋만 해도 판은 성립한다.

순서무엇을어느 Step참고처예상확실성
1시각 표기에 KST 명시① · ③Cal.com5분확실
2상태 배너를 최상단으로⑥ (② 동반)네이버 예약10분확실
3재선택 화면에 원래 희망 고정⑤Setmore15분확실
4슬롯별 대기 인원 표시③ 핵심TidyCal30분정책 SQL 의존

고정 규칙은 그대로다

  • 접수는 점유가 아니다 — 대기 인원을 보여줄 뿐, 신청을 막지 않는다. 오히려 이 규칙을 화면이 설명하게 된다.
  • 확정만 슬롯을 마감한다 — 변경 없음.
  • 확정은 어드민이 수동으로 누른다 — 변경 없음. 경합 수는 판단 근거일 뿐 자동 확정을 만들지 않는다.
  • 대기 수 제한은 기본에 없다 — 수를 보여줄 뿐 제한하지 않는다.
  • 디자인 범위 — 배지·배너 모두 기본 HTML 텍스트와 테두리로만 만든다. 아이콘·이미지·애니메이션은 넣지 않는다.
  • 권한 — 남의 신청 개수만 열고 신원은 열지 않는다. service_role은 브라우저에 넣지 않는다.
이 장의 초록 칸은 아직 하나도 만들지 않았다. v1의 보라 칸은 어제 만들어 동작을 확인한 것이다. ③의 감정 3→4는 관찰값이 아니라 기대 효과 가설이며, 만든 뒤 다시 확인한다. ④는 앱 바깥(개인 달력)이라 이번에도 손대지 않는다.
